# ホストSOPSの権限分離・段階移行

## 現在地（2026-10-26）

HostSopsは秘密値を返さずに発行・交換しますが、Windowsの同一ユーザーで
`coding_tools_exec_command` 等の任意コードを実行できる場合、そのユーザーは
SOPS/age鍵へ直接アクセスできます。キー別ポリシーは**誤操作防止**であり、
AIの秘密情報アクセスをOSレベルで遮断するものではありません。
当該coding-toolsプロセスの確認時点の管理者トークンは無効でしたが、
これだけで他の昇格経路がないことは証明しません。

## 移行の承認ゲート

1. 正本SOPS、age秘密鍵、既存Lomway PATと稼働クライアントの
   *秘密値を表示せず*、所有プロセス・OSユーザー・ACL・依存関係を調査する。
2. 専用の非管理者Windowsサービスアカウントを準備し、age秘密鍵とSOPS正本を
   **そのアカウントだけ**が読めるようにする。事前に復元可能な暗号化バックアップ、
   ロールバック手順、必要な人間の承認を用意する。
3. 利用先ごとに固定した用途・キー・許可ツール・最大有効期間を持つ
   最小権限のIPCを実装する。呼び出し元のOS IDまたは認証済みMCP主体を検証し、
   破壊的操作・高権限PATには明示的な人間の承認を要求する。
4. 戻り値はキー存在や発行結果等のメタデータだけとし、復号値、ハッシュ、
   トークン、環境変数へのSecret注入を任意のAI呼び出し元へ渡さない。
5. 隔離した合成SOPS/ageで成功・拒否・多重呼出・クラッシュ・復旧を試験し、
   既存のChatGPT/Lomway接続を維持できることを確認した後に切り替える。

## 非対応とする実装

- 同じWindowsユーザーでスクリプトを分けるだけの「隔離」宣言
- 汎用シェルからSOPSを復号できる状態でのセキュリティ保証
- AI自身による承認ポリシーの無制限な拡張
- 本番のPAT失効やage鍵移管を検証・ロールバックなしに実行すること

## 別途改善すべき周辺ライター

共有ロックは現時点でHostSopsとSopshelfの協調範囲だけです。
`provision-backend-token.ps1`、Praxiomのprovisionスクリプトなど、
別のSOPS直接更新経路を列挙し、正本と競合する経路について個別に
共通ロック・暗号化ステージング・安全な復旧へ移行する必要があります。
この文書は移行計画であり、現行のOS権限・MCP公開設定を変更しません。
